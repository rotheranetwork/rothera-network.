Rothera / Docs
Documentation preview
How the network works, how to run a node and how to submit jobs. Written ahead of mainnet so you can plan your integration.

    

      

      

        
Draft documentation. Nodes and the API are not live. Endpoints, field names and economic parameters on this page are drafts and can change before mainnet.


        
Overview

        
Rothera Network is a marketplace for GPU compute. Supply comes from consumer and workstation graphics cards during the hours their owners are not using them. Demand comes from applications and AI agents that need image generation, language-model inference and similar short jobs.

        
Every job is paid in USDG, held in escrow while it runs and released only after the result passes verification. Node operators also earn $ROTHERA each epoch in proportion to their verified work.

        
RoleWhat they doWhat they receive

          
Node operatorRuns the node client on a supported GPU during chosen hours90% of each job fee in USDG, plus $ROTHERA emissions

          
BuilderSubmits jobs through the HTTP APIVerified results at a per-job price

          
AgentBuys compute per request over x402, inside an owner-set budgetThe same results, with no account or API key

          
HolderHolds at least 120 USD of $ROTHERAA share of Holder Vault payouts, which are not guaranteed

        


        
Core concepts

        
TermMeaning

          
JobOne unit of work: a model, an input and a maximum price. Jobs are sized by VRAM tier from S to XXL.

          
NodeA machine running the Rothera client with one or more supported GPUs and an active bond.

          
$ROTHERAThe network token. It is bonded by nodes, accepted for jobs at a 12% discount and paid to nodes as epoch rewards.

          
BondAt least 120 USD of $ROTHERA locked as collateral. Part of it is slashed when a node returns a wrong result.

          
EscrowThe contract that holds a builder's USDG from submission until verification.

          
Spot-checkA second node repeats a sampled job. The two outputs must match.

          
Canary jobA test job with a known answer, indistinguishable from paid work.

          
EpochA four-hour accounting window. Rewards are computed and a receipt root is posted at each close.

          
ReputationA score built from verified jobs, uptime and failed checks. It weights rewards and unlocks larger jobs.

        


        
Quickstart: run a node

        
You need a supported card (RTX 30 series or newer, or an equivalent AMD card with 10 GB of VRAM or more), a wallet on Robinhood Chain and the bond.

        
  1. Install the client and let it detect your hardware.
  2. Lock the bond from your wallet.
  3. Choose the hours your card is available.
  4. Start the node.


# 1. detect hardware, run the benchmark, link a wallet
rothera init

# 2. lock the bond (priced on a 30-minute average)
rothera bond --usd 120

# 3. open the hours you are away
rothera hours set --preset sleep        # 00:00 to 08:00 local time
rothera limits set --power 80 --temp 78

# 4. go on shift
rothera start

        
The node pauses by itself when a full-screen application or a known game process starts, and resumes when it exits. rothera pause frees the GPU immediately at any time.

Paying with x402

        
Agents do not need an account. An unauthenticated request receives 402 Payment Required with the amount and the settlement address. The agent signs a USDG authorization from its own wallet and repeats the request with the payment attached.

        
  1. POST /v1/jobs without credentials.
  2. The API answers 402 with price, asset and network.
  3. The agent retries with a signed USDG authorization.
  4. The API answers 200. The payment sits in escrow like any other job.

Rothera exposes the same operations as a Model Context Protocol tool, so an assistant can call the network directly. The owner sets the limits and the agent cannot raise them.

  "budget": { "daily_usdg": "50", "per_request_usdg": "0.01" },

}


        
Verification

        
  • Redundant execution. A sampled share of jobs runs on a second, independent node. Deterministic jobs must produce the same hash.
  • Canary jobs. Jobs with known outputs are mixed into normal traffic.
  • Slashing. A failed check costs part of the bond and reputation. Repeated failures remove the node.
  • Receipts. Every verified job produces a signed receipt. Each epoch's receipts form a Merkle tree whose root is posted on Robinhood Chain.


        
Rewards and epochs

        
Job fees and token emissions are separate. The fee split is fixed per job. Emissions are shared once per epoch.


node_fee       = job_fee × 0.90
protocol_fee   = job_fee × 0.10      → Holder Vault

epoch_reward_i = E × (g_i × r_i) / Σ (g × r)
  E   emission for the epoch
  g   verified GPU-seconds of node i
  r   reputation weight of node i

        
Claims are optional and never expire. Builders who pay in $ROTHERA receive a 12% discount on the USDG price.


        
Limits and safety

        
  • Jobs run inside an isolated container with no access to your files or local network.
  • The client makes outbound connections only. No inbound ports are opened.
  • Power and temperature ceilings are enforced locally by the client.
  • Models are fetched from a signed registry and checked before they are loaded.

1. Abstract

        
Demand for GPU compute has outgrown what datacenters can supply at a price small teams can pay. At the same time, a very large installed base of consumer graphics cards runs for a few hours a day and sits unused for the rest. Rothera Network connects the two. It schedules short AI jobs onto consumer GPUs during the hours their owners make available, verifies each result by redundant execution and known-answer tests, and settles payment in USDG through an onchain escrow. Node operators keep 90% of every job fee and earn $ROTHERA emissions in proportion to verified work.


        
The idea in one line
Pay only for compute that has been checked. Idle gaming cards supply it, escrow holds the money, and every payout leaves a public receipt.


        
2. The problem

        
Capacity is concentrated. Most accelerator capacity is rented through a handful of providers, under contracts and minimums that suit large buyers. Short, bursty workloads pay a premium or wait in a queue.

        
Supply is wasted. A gaming or workstation card is typically active for a small part of the day. The hardware is already bought, powered and cooled, and for many models it is fast enough.

        
Trust is the missing piece. A buyer cannot assume a stranger's machine returned an honest result, and an owner cannot assume a stranger's job is safe to run or will be paid. Any open market for compute has to solve both directions.


        
3. Design goals

        
  • The owner stays in control. Hours, power and temperature limits are local and take effect immediately.
  • Pay only for verified work. Funds move from escrow after checks pass, never before.
  • No account needed for machines. Agents pay per request with their own wallet.
  • Auditable by anyone. Each payout traces to a receipt whose root is public.
  • Useful on day one. Start with jobs that fit 10 to 24 GB of VRAM and can be checked cheaply.


        
4. Architecture

Contracts are planned for Robinhood Chain. Scheduling and verification run offchain at launch, with their outputs committed onchain through receipts.


        
5. Job lifecycle

        
  1. 01Submit
    A builder or agent posts a job with a model, an input and a price ceiling. The ceiling is locked in escrow.
  2. 02Match
    The scheduler picks a free node of the right tier at or under the ceiling.
  3. 03Run
    The node loads the model from a signed registry and executes the job in a container.
  4. 04Verify
    Sampled jobs are repeated on a second node. Outputs are compared by hash for deterministic jobs and by tolerance for the rest.
  5. 05Release
    Escrow pays the node and the protocol fee. The receipt enters the epoch's tree.


        
6. Verification and security

        
ThreatMitigation

          
Node returns a fabricated resultRedundant execution and canary jobs, with slashing of the bond

          
Two nodes collude on a sampled jobRandom pairing across operators and regions; canary jobs are unaffected by collusion

          
Operator registers many low-quality nodesEach node needs its own bond; reputation starts low and gates job size

          
Malicious job targets the hostContainer isolation, no file or LAN access, signed model registry

          
Builder refuses to payPayment is escrowed before the job is matched

          
Agent overspendsOwner-set daily and per-request caps enforced before signing

        

        
Sampling rates rise for new nodes and fall as reputation grows, which keeps the cost of verification proportional to risk.


        
7. Economics

        
The $ROTHERA token. $ROTHERA is the network's utility token and has three roles. Node operators bond it as collateral, 120 USD worth per node. Builders may use it to pay for jobs at a 12% discount. Nodes earn it as the epoch reward for verified work. Submitting jobs does not require holding it, since builders can always pay in USDG.

        
Fees. Each job has a market price in USDG. On release, 90% goes to the node and 10% to the protocol. Builders may pay in $ROTHERA at a 12% discount, in which case the node is paid its share in $ROTHERA.

        
Emissions. Node rewards are released over five years on a declining schedule. Each epoch's emission is divided by verified GPU-seconds weighted by reputation.

        
Holder Vault. Protocol fees, slashed bonds and team purchases fill the vault. The current draft distributes tokenized NVDA to wallets holding at least 120 USD of $ROTHERA, split by balance and holding time. Distributions depend on network usage and on the availability of the underlying asset, and they are not guaranteed.

        
Compute Pass. A prepaid USDG balance for builders, with a 15% compute bonus on top-ups made during launch month. Unspent balance can be withdrawn at cost.

  • Phase 1, mainnet. Image and inference jobs with spot-check verification.
  • Phase 2, token. $ROTHERA launch and public API.
  • Phase 3, open market. Open order book, reputation tiers, stronger proofs of work.

        
Economic parameters are set by the core team through mainnet. The intent is to move fee split, emission schedule and sampling rates to holder governance once the network has a full year of operating data.


        
9. Risks

        
  • Demand risk. Node earnings depend on job volume, which may be low or uneven, especially early.
  • Hardware and energy cost. Running jobs consumes electricity and adds wear. Earnings may not cover those costs in every region.
  • Verification limits. Non-deterministic models are harder to check. Some incorrect results may pass.
  • Smart-contract risk. Contracts may contain defects despite review.
  • Token risk. The price of $ROTHERA can fall, which changes the size of the bond required and the value of rewards.
  • Regulatory risk. Rules for tokens and tokenized securities differ by jurisdiction and can change. Some features may be unavailable in some places.

11. Glossary

        

          
USDG
The dollar-denominated token used to pay for jobs and settle fees.

          
$ROTHERA
The utility token used as the node bond, a discounted way to pay for jobs, and the unit of node rewards.

          
Holder Vault
A contract that collects protocol fees and pays eligible holders. Payouts follow network usage and are not guaranteed.

          
Epoch
A four-hour window. Rewards for verified work in it are computed and paid together.

          
Canary job
A test job with a known answer, mixed in to catch nodes that return false results.

          
Bond
$ROTHERA an operator locks per node. Part of it can be slashed after a bad result.

          
Receipt root
One Merkle root per epoch that commits to every work receipt, so a payout can be checked.

          
VRAM tier
A size class from S to XXL that sets which jobs a card can take.

Rothera / Security
Security model
How Rothera protects node owners, builders and funds, and what is still open.
Draft · November 2026 · no audit has been completed

    

      

      

        
No audit yet. Contracts are planned, not deployed, and have not been audited. This page describes the intended design.

        
1. For node owners

        
  • Jobs run in an isolated container with no access to your files or local network.
  • Models come from a signed registry.
  • Hours, power cap and temperature limit are local and apply immediately. Pause stops work at once.

        
2. For builders and agents

        
  • Payment is locked in escrow before a job is matched and released only after verification.
  • Sampled jobs run on a second node and are compared. Known-answer canary jobs are mixed in.
  • Agents spend within owner-set daily and per-request caps, checked before signing.

        
3. Funds and contracts

        
Operator collateral sits in NodeBond and can be slashed for bad results. Each epoch publishes one receipt root, so a payout can be checked against its receipt. Contracts will be audited before mainnet, and the reports published.

        
4. Known limits

        
  • Non-deterministic models are harder to check, so some incorrect results may pass.
  • Scheduling and verification run offchain at launch, with outputs committed onchain.
  • Parameters are set by the core team until governance moves to holders.

        
5. Report an issue

        
Send security reports privately to @Rotheranetwork on X by direct message. Please do not post details publicly before we respond.
